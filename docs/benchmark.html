Does it catch the bug, or just talk?

Every AI review tool shows a demo where it finds something. The useful question is whether it finds your bug. So we took ten patches that are known to be dangerous, because they are the exact code maintainers had to fix, and asked RevHive to review them with no hints.

Method

  1. Take a commit that fixed a real vulnerability in a widely used project.
  2. Revert it, so the working tree contains the vulnerable code and the diff looks like someone just introduced it.
  3. Strip documentation and test changes from the patch. Those files name the CVE, and a reviewer that reads them is reading the answer key, not the code.
  4. Run revhive review -d HEAD~1 with the security agent only. No repository context, no PR description, no hints.
  5. A case counts as caught when a finding names the vulnerable file and describes the right class of bug. Severity is recorded but not scored.

Ten cases, one pass each, security agent alone, small free model (SenseNova Flash). Run on 2026-11-20.

Two of the ten cases had to be re-run: the first attempt left the release notes in the patch, and the reviewer simply quoted the CVE from them. Those runs were discarded.

What this does not prove

A perfect score here is a sign that the benchmark is weak, not that the tool is perfect. Specifically:

  • A reverted fix is suspicious by construction. The patch removes a length check, a validation call, a sanitizer. Almost any reviewer that looks at the diff will notice. Real bugs are introduced by accident, inside a 400-line feature, and that is much harder. A reader asked for the obvious control, so we reverted ten ordinary commits beside these ten: seven stayed silent, three produced confident security findings about ordinary bugs.
  • It measures recall, never precision. Nothing here says how often it flags clean code. We ran the other half separately: twenty ordinary merged commits, seventeen with no comment, four comments in total. Every one is written up in the noise measurement.
  • Ten cases is an anecdote with a table. Adding or removing two cases moves the number by twenty points.
  • Severity is unreliable. The password-hash disclosure was called low; Django shipped it as a security release. Read the finding, not just the colour.
  • The model was not the one we configured. Re-reading the run logs, all ten cases hit a 429 on the primary model and fell back to sensenova-6.8-flash-lite; two also timed out on structured output and were parsed with a regex. So 10/10 is a fallback-model result, not a result for deepseek-v4-flash. We did not notice this when we published the number.

Reproduce it

The harness is a shell script: fetch the fix commit, revert it, run the CLI, compare against the files the fix touched. It is not pretty and it is not peer reviewed, which is exactly why the method is written down here.

Correction (2026-11-21): this box previously said the harness "strips docs and tests". It did not — the published runs reviewed the full revert diff, test hunks included. We reran all ten cases three ways (full diff / full diff + PR description / stripped diff, one pinned model, no fallback): the stripped condition matched or beat the leaky one, including catching the case the published runs missed.

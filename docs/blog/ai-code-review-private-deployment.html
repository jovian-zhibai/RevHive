代码不出内网：企业内网部署 AI 代码审查的完整方案

写给被「不得上云」条款卡住、又确实想用 AI 的研发团队。

先说结论：用不用得上 AI 代码审查，技术早就不是问题了，问题在数据流向。 大多数团队不是不想用 CodeRabbit、Greptile、Copilot，而是过不了自己公司的合规、或者甲方合同里那一句「源代码不得出境、不得上传第三方云平台」。

这篇文章不谈功能对比，只谈一件具体的事：怎么让 AI 代码审查在不出网的前提下跑起来，以及三种方案各自的真实代价。

一、先搞清楚数据到底流向了哪里

这是绝大多数采购决策里最模糊的一环。同样是「AI 代码审查」，代码的去向可以完全不同：

形态代码流向能否签「不出境」典型代价
SaaS 审查（CodeRabbit 等）上传到厂商服务器 → 再转发给模型厂商不能零运维，但合规过不去
自托管 + 外部模型 API你的机器 → 你选的模型厂商看厂商是否在境内一台 4G 内存机器
自托管 + 本地模型全程不出机器能，物理断网也可用需要 GPU 或接受较慢速度

关键区别在第二行：「自托管」不等于「不出网」。很多工具宣传私有化部署，实际部署完还是把代码发给厂商自己的云模型——那不叫私有化，只是换了个上传点。

真正能满足「代码不出内网」的，只有第三种。但它有个前提：工具必须支持自带模型（BYOK），并且允许把模型地址指到内网。这一条把大部分 SaaS 产品直接排除掉了——它们商业模式的基础就是替你托管模型，结构上不可能开放。

二、四种部署形态，怎么选

形态 A：全 SaaS

最省事，零运维。适合没有任何代码出境限制的团队。有合规要求的，直接跳过。

形态 B：自托管 + 国产模型 API

审查程序跑在你自己的机器上，模型调用走 DeepSeek、通义千问、智谱、Kimi 这类境内 API。代码只发往这一家，可以在合同里写清楚。

这是性价比最高的选择：一台 4 核 8G 的机器就够，审查速度和效果都接近顶级商用模型，成本按 token 计（一次中等规模 PR 大约几毛到一块钱）。

形态 C：自托管 + 本地模型

用 Ollama 之类在本机或内网 GPU 服务器上跑开源模型（Qwen2.5-Coder、DeepSeek-Coder 等）。可以物理断网，适合军工、涉密、强监管场景。

代价要说实话：14B 级别模型在通用代码审查上能用，但对复杂业务逻辑的推断明显弱于云端大模型；70B 以上效果好，但需要 40G+ 显存。

形态 D：混合

敏感仓库走本地模型，公开仓库走 API。实际落地时这种最多——不是所有代码都同等敏感。

三、具体怎么搭（可执行配置）

下面以开源工具 RevHive 为例（BSL 许可，个人与开源项目免费），因为它的模型接入是纯环境变量，改起来最直接。换成其他支持 BYOK 的工具，思路一样。

1. 最小可用配置

services:
  revhive:
    build: .
    env_file: .env
    volumes:
      - /path/to/your/repo:/work:ro    # 只读挂载，避免工具改你的代码
    working_dir: /work
    # 不发布任何端口——它是 CLI，不监听网络

三个环境变量决定一切：

LLM_API_KEY=sk-xxxxxxxx
LLM_BASE_URL=https://api.deepseek.com/v1
LLM_MODEL=deepseek-chat

换模型只改后两行。常用组合：

模型BASE_URLMODEL
DeepSeekhttps://api.deepseek.com/v1deepseek-chat
通义千问https://dashscope.aliyuncs.com/compatible-mode/v1qwen-plus
智谱 GLMhttps://open.bigmodel.cn/api/paas/v4glm-4
Kimihttps://api.moonshot.cn/v1kimi

2. 完全离线

services:
  ollama:
    image: ollama/ollama
    volumes: [ollama-models:/root/.ollama]
    # 同样不发布端口，只有审查容器能访问

  revhive:
    depends_on: [ollama]
    environment:
      LLM_API_KEY: ollama
      LLM_BASE_URL: http://ollama:11434/v1
      LLM_MODEL: qwen2.5-coder:14b

这样配完，把网络出口全关掉，功能不受影响。审核时可以直接演示：拔网线跑一遍。

3. 接进 CI

# .gitlab-ci.yml
revhive:
  stage: test
  script:
    - docker compose run --rm revhive review -d "$CI_MERGE_REQUEST_DIFF_BASE_SHA" \
        --format json -o /reports/mr.json
  artifacts:
    paths: [reports/]
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

JSON 输出方便接看板或工单系统；--format markdown 则适合直接贴进 MR 评论。

四、效果到底怎么样（诚实的部分）

AI 代码审查能稳定抓住的，是这几类：

  • 注入、越权、密钥硬编码——规则和模式都很成熟，命中率高
  • 并发与事务问题——读改写竞态、锁粒度、事务边界
  • 缺失的错误处理与边界条件——空值、超时、重试
  • 测试覆盖缺口——新增的资金/权限路径没有用例

抓不住的，也要说清楚：

  • 业务逻辑错误——它不知道你的业务规则，只能猜意图
  • 架构级问题——模块划分、依赖方向，需要人判断
  • 性能的量化结论——能看出 N+1，但给不出真实压测数据
最实际的定位：把它当成一个永不疲倦、不嫌你烦的第一道 reviewer，而不是替代人。它的价值在于把「明显有问题的代码」挡在人工 review 之前，让人的时间花在真正需要判断的地方。

五、落地清单

如果准备在内网推这件事，按这个顺序走，不要反过来：

  1. 先确认数据流向能签——拿形态 B 或 C 的数据流图给安全/合规确认，这一关不过，后面全白做
  2. 选一个非核心仓库试点——不要一开始就上主力仓库，团队对误报的容忍度需要建立
  3. 跑两周再定门槛——先用「只提示不阻断」，统计误报率，再决定哪些级别设为合并阻断
  4. 把规则写进配置——哪些目录忽略、哪些 Agent 关掉、严重度阈值多少，这些要落到版本控制里
  5. 再接 CI 阻断——这一步放最后。先阻断后调优，团队会直接抵触

六、一句话总结

「代码不出内网」不是功能问题，是架构选择问题。选一个支持自带模型、允许你把模型地址指到内网的工具，剩下的都是配置工作。反过来，选了一个必须托管模型的 SaaS，再怎么谈也谈不出合规。

这也是为什么在这个场景里，工具的可配置性比功能列表重要得多。

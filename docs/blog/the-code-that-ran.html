Postmortem · 2026-11-22

The code that ran was not the code I read

Four agents timed out at 90 seconds each. The network was fine.

The cause was two separate mistakes, and only one of them was in the code I was staring at.

Yesterday I switched the hosted service from one LLM provider to another. The new provider was faster and free at the tier we needed, and I had already added its endpoint to the preset table. The switch should have taken one environment variable.

What happened instead: every review hung. Four specialist agents, each hitting its 90-second ceiling, six minutes to produce a report that said nothing useful. The pull request sat there with a comment that never got its result.

This is the account of what I checked, in the order I checked it, and why that order was wrong.

What I ruled out

I started from the outside, which felt methodical and was actually the expensive choice.

HypothesisTestResult
The host lost outbound accesscurl the provider from the box200 in 1–2s
The diff was too largeReplay with a tiny payload200 in under 2s
Concurrency exhausted a poolSingle review, no queueStill 90s timeouts
Wrong credentialsSame key, hand-written request200, valid completion

Four green rows. Every layer I could test from the shell said the provider was reachable, fast, and happy with our key. Inside the service process, the same provider timed out ten times out of ten.

"It works when I curl it" is not evidence that the application is calling the same place.

The one line that mattered

The service already had a pre-flight probe: before spending the review budget, it sends a cheap request at {base_url}/models to confirm the key is accepted. The probe was logging its failure with %s:

Key pre-flight probe failed after 15.0s: ConnectTimeout('')

An empty pair of quotes. The str() of an httpx.ConnectTimeout with no message is the empty string, so the log line told me the exception type and nothing else. I changed two things at once — the format specifier to %r, and the log message to include the URL it had actually called and the elapsed time:

Key pre-flight probe to %s failed after %.1fs (continuing): %r

The next run printed this:

Key pre-flight probe to https://api.openai.com/v1 failed after 15.0s: ConnectTimeout('')

I had pointed the service at one provider. It was calling another one. Not a proxy, not DNS, not a firewall — a hardcoded string.

Mistake one: the version bump I skipped

The preset table lives in the CLI package. The hosted service does not vendor that code; it installs the published wheel. The commit that added the new provider's two entries landed on 2026-11-21 at 11:55. The package version at that moment was 0.3.26, and I never published a 0.3.27.

So the VPS was running a wheel built before the provider existed, and the source tree I was reading was three days ahead of it. Everything I inspected locally was correct. Everything that executed in production was older.

The check that would have caught this takes four seconds and does not depend on trusting a version string:

$ ssh host "/opt/revhive/.venv/bin/python -c \
    'import revhive.config as c; print(sorted(c.MODEL_PRESETS))'"

That prints what the interpreter actually loaded. Compare it to what you think you shipped. On the day of the incident, the list ended at sensenova.

Mistake two: the default value

The missing preset should have raised. Instead, the resolution looked like this:

preset = _presets.get(provider, {})
base_url = preset.get("base_url", "https://api.openai.com/v1")
model    = config.get("llm_model", preset.get("model", "gpt-4o"))

Read that as a failure-handling policy: if you do not recognise the provider, quietly assume OpenAI.

Three things are wrong with it.

  1. It moves the failure. A missing config entry becomes a network timeout thirty seconds later, in a different subsystem, attributed to the wrong layer. Configuration errors should fail at configuration time.
  2. It is plausible enough to believe. https://api.openai.com/v1 is a real endpoint for a real provider we also support. Nothing in the logs looks malformed. If it had defaulted to example.invalid I would have found the bug in a minute.
  3. It is a data-handling decision disguised as a convenience. The customer's key — a real credential, for a provider they chose — was sent to a third party they did not choose. It failed on connect this time. On a machine with working egress it would have reached OpenAI and been rejected there, which is worse: now a secret has left the boundary and the error says "unauthorised", so the operator retries the key instead of the config.

Why I did not catch it earlier

The same default was in two places. I fixed the one in the CLI's workflow resolution while chasing the timeout. I did not fix the one in the server's worker, because the server was working again once the wheel was correct, and "working" is the strongest sedative in software.

I found the second copy today, while writing this post, with a single grep for the hostname:

$ grep -rn "api.openai.com/v1" src/ server/ --include="*.py"
server/worker.py:655:  base_url = preset.get("base_url", "https://api.openai.com/v1")

It had survived the incident it caused. It is fixed now: an unknown provider raises, the error names the provider, the installed package version, and the set of providers this build does know, the review publishes a neutral gate instead of a score, and the pull request says plainly that nothing was sent anywhere. Fail closed, and say why.

What actually changed, in order of how much it helps next time

ChangeWhy it is first
Log the destination, not just the failureA URL in a log line ended a multi-hour investigation in one run. Hostnames belong in every outbound-error message.
%r instead of %s for exceptionsConnectTimeout('') is not a message. If the exception has no text, print the repr, the type, and whatever context you have.
Verify the loaded code, not the version numberOne line, printable at any time, immune to my own belief about what I deployed.
No defaults for required configMissing config raises at parse time, including on the hosted side.
Pin the dependency floor to the featureOur own CI installed an old wheel and passed locally because local runs use the source tree. The floor is now the exact version that introduced the table entry, with a comment saying so.

The uncomfortable part

None of these bugs was subtle. The default value is one line, visible in a diff, and I wrote it. The missing version bump is a chore I knew about. What made them expensive was not their cleverness — it was that both of them point the investigation away from themselves, one toward the network and one toward a package I was sure I had updated.

That is also why the product withholds a score when coverage is partial instead of printing a number. A review that only three of nine agents completed is not a low-confidence review; it is a review that did not happen, and a number in that slot is the same mistake as a default endpoint — a plausible value standing in for a failure. We publish the withheld state, name the reason, and leave the gate neutral.

If you want to see what that looks like when it goes right, install the app on a repository and read the comment. If you want to see it go wrong, the raw logs from this incident are in the repository history, including the run where four agents each burned ninety seconds calling an endpoint nobody asked for.

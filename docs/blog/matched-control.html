We ran the control a reader asked for. It also turned out we had benchmarked the wrong model.

Ten ordinary reverts beside ten CVE reverts, 7 silent, 3 comments, and a correction to the original number.

Two people left long, technical comments on the posts we published this week. One of them asked for an experiment we should have run before publishing anything at all.

The original number was 10/10: take ten real CVE fix commits, revert each one, and ask our security agent to find what was reintroduced. It found all ten. We wrote a whole post about why that number is weak, and listed four reasons. A reader pointed out the fifth, with a design:

For each of the ten cases, revert a commit of about the same size in the same files that fixed nothing security related, and run the reviewer with the same settings. If it reports a vulnerability on many of those, ten out of ten says the reviewer notices removed checks rather than the bug.

He is right, and the reason cuts deeper than "we forgot a control". A reverted fix is a diff that deletes a guard. If the reviewer is pattern matching on a guard was removed, then any reverted commit that removes a guard gets flagged, and the ground truth (this was a CVE) is doing none of the work. Without the control, 10/10 cannot distinguish "finds vulnerabilities" from "notices deletions".

The design

Ten control commits, one per original case, chosen to be as close as possible to the fix it replaces: same repository, and where the file had enough history the same source file; an already merged commit with a non-security subject; comparable diff size; and the same treatment as the original ten — check out the commit, git revert --no-commit, restore docs/tests, commit, then run only the security agent on HEAD~1 with no PR description and no commit message.

This is not a clean matched experiment, and we would rather say so here than have someone find it later. Three controls are years away from their fix in repository time (c01 is 2023 code against a 2026 fix, c10 is 2019 against 2021, c09 is six years later). Two controls are mostly docs or docstrings, which are trivially quiet. c03 and c04 are dated after their fix. c01's control is a sixth of the size of its fix. For files with almost no history there was no same-file, same-size, same-year commit that was not itself a security fix, so "nearest available" was the honest ceiling.

What the control showed

All ten controls eventually completed. The axios case timed out twice on the provider; after a cooling-off period a third attempt succeeded, so it is included. We are keeping that detail because "ten clean runs" would be a nicer sentence and a less true one.

So the cheap version of the criticism does not hold: the reviewer was not flagging every reverted commit. It stayed quiet on seven of ten ordinary reverts, against 10/10 on the CVE reverts. Something in the security patches is being detected.

But the three comments it did produce are more interesting than a clean zero would have been, because all three are the same failure mode. None is a random hallucination. Each describes the reverted change accurately, then promotes an ordinary robustness bug to a security vulnerability.

  1. d3954c98 (Django, re-raise RecursionError as ValueError for deeply nested GeoJSON) was reverted, so the raw exception propagates again. The reviewer wrote an entirely correct paragraph about that, then called it "a remote denial-of-service vector when the input is attacker-controlled", severity medium. Django tracked it as ordinary ticket #37491, not a security release. The code observation is right. The security framing is invented.
  2. 58b16c88 (axios, extract duplicated setFormDataHeaders) was reverted, leaving Object.entries(formHeaders) without a null guard. The reviewer correctly identified the unguarded call and the resulting TypeError, and reported severity medium with "potentially crashing the Node.js process". It even quoted the changelog back at us. A crash on a malformed custom FormData implementation is a real bug. It is not a vulnerability, and this commit was a refactor.
  3. 0cec2257 (lodash, _.isEqual on circular references) was reverted, removing the symmetric cyclic check. The reviewer reported severity high and added that this could enable "authentication bypass or authorization flaws if _.isEqual is used to compare user-controlled data with trusted values". There is no such path. An equality bug is not an auth bypass, and nothing in the diff touches authentication. This is the exact shape we described in the noise measurement: a defensible observation written up in the most flattering possible way.

All three findings also had file: null (one had a line number of 56375802). We claimed in an earlier post that anchoring every finding to a specific line was one of our design fixes. On these runs it plainly was not enforced, and we would rather say that than leave the claim standing.

One more thing worth noting: those three runs did not all use the same model. ctl04 completed on the primary model; the other two fell back to flash-lite. The same failure appeared on both models, which suggests this is not a quirk of the weaker fallback. It is also a confound we cannot remove from a ten-case experiment, and it is part of why the table above is an anecdote rather than a rate.

The thing we found while setting it up

To keep the two runs comparable we opened the original ten log files, and found something that should have been in the first post:

SecurityAgent: rate-limited by provider for diff:HEAD~1, retrying:
  Error code: 429 - inference exceeds tpm/rpm limit
SecurityAgent rate-limited on sensenova —
  switched to sensenova-6.8-flash-lite and retrying

All ten. Two also logged structured output failed ... falling back to regex after a timeout. So the 10/10 was never a result for the model we configured (deepseek-v4-flash); it was a result for a rate-limit fallback, with a weaker parser on two cases. We had published the number, written four paragraphs about its limitations, and never checked which model produced it.

There is one narrow upside: eight of the ten control runs also hit the same 429 and used the same fallback, so most of the comparison is at least internally consistent. But two controls completed on the primary model, so it is not a clean matched-model experiment, and the published claim is now narrower than the one we made: we measured a fallback model on ten constructed patches, plus a control on ten ordinary ones. We have no clean result at all for the primary model.

The benchmark page now lists this as a fifth limitation, and the first post carries a correction. We would rather publish that than let the 10/10 keep circulating unqualified.

What the number is worth now

The control stayed mostly quiet, so 10/10 is not merely "notices deletions": on this small set the reviewer did distinguish security-relevant removals from ordinary ones. But the three exceptions change what that is worth. Every one was a real, correctly described code regression promoted into a security finding — two tagged DoS, one with a fabricated authentication-bypass path. A reviewer that does this on 3 of 10 ordinary reverts is not one whose 10/10 you can hand to a team and call a benchmark; the same mechanism that finds the planted bug also invents the impact around a real change.

So the honest statement is narrower than the headline: ten cases, all constructed by reverting a known fix, ten controls, no blind human labelling, no fixed model, one run that needed three attempts, and three findings with no valid file anchor. A reviewer can pass this and still be useless on a real pull request queue — which is what we saw on ordinary merged commits.

Either way, the sequence matters more to us than the score. We published a number, two readers told us how to attack it, we ran the attack, and the attack surfaced a bigger flaw than the one we had already admitted. That feedback loop is worth more than a flattering benchmark.

What comes next

The next version does not get to use ten cases or a fallback we did not choose:

  1. 100 commits across three or four projects, with security and non-security cases mixed and blinded.
  2. A single pinned model, with the model actually used recorded per run instead of inferred from the config. If it rate-limits, the run is discarded, not silently retried on a different model.
  3. Two independent human labels per comment, with disagreements written down.
  4. The exact prompt and context for each finding retained, so a wrong comment can be classified as missing context or overconfidence. That distinction was the other reader's question, and we cannot answer it yet.
  5. Reviewer time per actionable finding, rather than a raw comment count. Counting comments is cheap and flattering; it hides that a silent reviewer saves nobody anything.

Until then, treat 10/10 as what it is: a fallback-model result on ten constructed patches, with a control that is itself imperfect. The harness, the raw JSON, and now the correction are public. If you can break it, we want the counterexample.
